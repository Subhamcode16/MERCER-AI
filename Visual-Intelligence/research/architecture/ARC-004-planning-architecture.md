# ARC-004: Planning Architecture

## Purpose

The **Planning Architecture** defines how the platform transforms abstract user intent and semantic definitions into explicit, structured execution plans.

While the `Creative Context` (ARC-002) holds current Hypotheses and Facts, and the `Runtime` (ARC-003) executes Tasks, the Planning Architecture introduces specific `Planning Tasks` that bridge the gap between "What the user wants" and "What the Renderer needs."

---

## 1. The Principle of Centralized State

### Planning Principle
> A Plan is not a new state container. A Plan is a **Verified Plan** generated by a Planning Task, stored directly inside the Creative Context.

This prevents fragmentation. By treating a Plan as just another Context Fact, we ensure that:
- It can be easily accessed by all subsequent Tasks.
- It is subject to the same Confidence and Evaluation constraints as any other Hypothesis.
- It explicitly references the active DNA.

### Architecture Invariant
> Planning outputs structured decisions.
> Planning MUST NOT generate renderer-specific instructions.
> Renderer translation belongs exclusively to the Prompt Compiler.

This invariant completely prevents architectural leakage. A plan must remain semantic and mathematical.

---

## 2. Iterative Hierarchical Planning

Planning is not a linear sequence; it is a recursive, iterative loop. Evaluation tasks continuously review generated plans and trigger updates.

```
Campaign Plan
  ↓
Scene Plan
  ↓
Shot Plan
  ↓
Evaluation
  ↓
Scene Plan Updated
  ↓
Shot Plan Updated
```

### A. Campaign Plan
The highest-level structure.
- **Owner:** `Marketing Intelligence`
- **Output:** A structured list of Deliverables (e.g., "3 Instagram Posts, 1 Website Banner").
- **State Update:** Added to Context as `Verified Plan: Campaign Plan`.

### B. Scene Plan
The semantic constraints for a specific deliverable.
- **Owner:** `Creative Decision Engine` (orchestrating `Scene Intelligence` and `Lighting Intelligence`).
- **Output:** Semantic definitions (Location, Lighting, Mood).
- **State Update:** Added to Context as `Verified Plan: Scene Plan`.

### C. Shot Plan
The explicit, physical framing required before rendering.
- **Owner:** `Photography Intelligence` / `Directorial Intelligence`.
- **Output:** Camera angle, focal length, specific poses, character placement.
- **State Update:** Added to Context as `Verified Plan: Shot Plan`.

*(Note: For video, this hierarchy seamlessly extends to Campaign -> Sequence -> Scene -> Shot -> Frame).*

---

## 3. Plan Structure and Constraints

Every generated plan MUST follow a strict structural output to preserve explainability and ensure constraints are mathematically enforceable.

### The Required Output Structure
1. **Intent:** What is the creative goal?
2. **Constraints:** The strict boundaries that cannot be violated.
3. **Alternatives:** What other options were considered but discarded?
4. **Chosen Plan:** The final structured decision.
5. **Reason:** The logical justification linking back to Evidence/DNA.

### Example: Scene Plan Constraints
```yaml
Scene Plan:

Goal:
Luxury Royal Atmosphere

Constraints:
- Outdoor
- Aspect Ratio: 9:16 (Instagram)
- Lighting: Golden Hour
- Budget Constraints Apply

Success Criteria:
- Luxury Score > 0.9
- Product Visibility > 0.95
```
By encoding Success Criteria directly into the Plan, Evaluation Tasks can mathematically score the outputs.

---

## 4. Conflict Resolution in Planning

Because Plans are nested Facts in the Context, conflicts are resolved systematically by the Decision Engine before execution.
- If the `Brand DNA` requires "Bright Lighting" but the `Scene Plan` proposes "Midnight Silhouette", the Evaluation Task flags the conflict against the constraints.
- The Runtime pauses or retries the Planning Task with explicit failure constraints.

---

## 5. Acceptance Checklist Validation

As per `research-methodology.md`, this specification has been evaluated against the 10-year standard:

1. **Is this a universal concept?** 
   **Yes.** Any complex creative workflow requires hierarchical planning (Campaign -> Scene -> Shot) before rendering.
2. **Is it implementation-independent?** 
   **Yes.** This structure works whether the renderer is Midjourney, a 3D engine, or a human photographer.
3. **Does it have exactly one responsibility?** 
   **Yes.** It strictly defines the structural hierarchy of plans and how they are generated as Tasks. It does not handle memory or execution.
4. **Does it reduce complexity?** 
   **Yes.** By forcing Plans to exist as `Verified Plans` within the `Creative Context`, we eliminate the need for parallel state-sync mechanisms.
5. **Can another abstraction replace it?** 
   **No.** Without a Planning architecture, the system would attempt to map raw user intent directly to rendering prompts, leading to chaotic and inconsistent outputs.
6. **Has it survived at least one workflow validation?** 
   **Yes.** This mirrors the exact Phase 4 (Creative Reasoning) step in `VAL-001`.
7. **Does it introduce unnecessary coupling?** 
   **No.** Planning Tasks are standard Tasks conforming to ARC-003, perfectly decoupled via the Context.
