# RES-005: Knowledge Claim Model

## Purpose

The **Knowledge Claim Model** is the universal data contract for the Visual Intelligence Factory (VIF).

The VIF no longer extracts "attributes". An attribute is a static value (e.g., `Color = Red`) that lacks context, provenance, or justification. Instead, the VIF extracts **Knowledge Claims**.

A Knowledge Claim is a scientific assertion made by a specific model, at a specific time, backed by specific evidence, and subject to human verification. Every single piece of intelligence extracted in Processing Stations 3, 4, and 5 must be wrapped in this universal schema.

This ensures that the final Knowledge Graph (Processing Station 7) is not a database of assumed facts, but a ledger of *validated claims*.

---

## 1. The Knowledge Claim Schema

Every extraction produces a JSON/YAML object conforming to the following structure:

```yaml
KnowledgeClaim:
  # Identity
  ClaimID: "uuid"
  AssetID: "uuid"
  Timestamp: "iso-8601"

  # The Assertion
  Subject: "Garment"         # Mapped from Ontology V2 (e.g. VIO-005)
  Predicate: "IsA"           # Mapped from Ontology V2
  Value: "Saree"             # The extracted value

  # Example: Visual Craft Claim (VIO-009)
  # Subject: "Scene"
  # Predicate: "Lens"
  # Value: "85mm"

  # Scientific Rigor
  Confidence: 0.98           # 0.0 to 1.0
  Evidence: 
    - "Unstitched fabric drape over shoulder"
    - "Pleated fabric tucked at waist"
  
  # Provenance & Source
  SourceRegion:              # Where in the image did we find this?
    - [x_min, y_min, x_max, y_max]
  ProducingModel: "vif-garment-topology-v2.1"
  
  # Verification Lifecycle
  VerificationStatus: "Pending" # [Pending, Approved, Rejected, Corrected]
```

---

## 2. Evidence: The Core Differentiator

The introduction of the `Evidence` array is the most critical shift in this architecture.

**Why Evidence?**
If the model extracts `Value: Banarasi`, and the human reviewer disagrees, a simple "Reject" button is useless for training. 

By requiring the model to generate plain-text `Evidence` (e.g., `"Heavy gold zari border", "Floral brocade motifs"`), the human reviewer can see exactly *why* the model made a mistake. Did it hallucinate the border? Did it misinterpret Kanjeevaram motifs for Banarasi? 

This allows the human to provide specific corrections, turning the Human-in-the-Loop interface (Processing Station 6) into an active training data generator.

---

## 3. Lifecycle of a Claim

1. **Generation:** A micro-model in Processing Station 3 or 4 generates a claim. Its `VerificationStatus` is `Pending`.
2. **Confidence Routing (Station 6):**
   - If `Confidence >= 0.95`, the claim is automatically promoted to `Approved`.
   - If `Confidence < 0.95`, the claim is paused and routed to human review.
3. **Human Review:** A reviewer assesses the claim and its evidence. They can:
   - Mark as `Approved`.
   - Mark as `Rejected` (Claim is destroyed).
   - Mark as `Corrected` (The reviewer overwrites the `Value` and provides a reason).
4. **Graph Construction:** Only claims with `Approved` or `Corrected` status are allowed to become nodes and edges in the Knowledge Graph (Processing Station 7).

---

## 4. Architectural Boundaries

- **Single Format:** The Knowledge Claim schema is identical whether the claim is about Fashion (`VIO-006`), Styling (`VIO-007`), or Visual Craft (`VIO-009`). 
- **Plain-Text Evidence:** For V1.0 of the architecture, Evidence consists of plain-text strings generated by the Vision-Language Model. In V2.0, Evidence strings may be parsed into independent, nested Knowledge Claims.
